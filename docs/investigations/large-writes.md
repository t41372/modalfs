# Large-write failure investigation

Branch: `feat/stabilize-large-file-writes`. Baseline: `cc99faf` (installed application reports `c3c01d3`; the relevant VFS, NFS and daemon mount code has no diff). Investigation started on November 4, 2026.

## Incident evidence

The user copied several large files from another partition of a local macOS disk using Finder. Finder reported error 100060, and listing the destination reported OS error 60. The user reports no VPN, proxy or network switch and no sleep/wake around the failure. The app continued to show both volumes mounted. These observations alone do not identify a cause.

Read-only inspection of the running application found:

- The cache limit is 2 GiB. At inspection there are no pending journals or pending bytes. The affected volume reports 1,319,119,346 uploaded bytes, four commits and no errors. Its last recorded nonempty commit was 1,319,108,608 bytes at 03:03:55 (America/Phoenix). Two other destination files had only zero-length commits in the log.
- Both the lock-free Unix `/api/ping` and Unix `/api/state` answer successfully. Short process samples show sleeping threads, not a CPU loop. A sample of a stripped Go executable cannot establish goroutine lock ownership.
- Both NFS listening descriptors and the browser HTTP listening descriptor are still open in the daemon, but `lsof` reports all three TCP sockets as CLOSED. They are absent from `netstat`, and independent TCP connects to all three return ECONNREFUSED. `nfsstat -m` marks both mounts not responding. This is stronger evidence than a slow request or a cache backlog.
- No matching kernel/network-extension log was found in the narrow incident interval. Absence of logs is not evidence that no kernel event occurred.

No user mount, pending write, process or setting was changed to obtain this evidence. Raw local diagnostics are kept outside the repository; account identifiers, credentials and user filenames are not needed in this report.

## Initial questions and experiment design

The initial evidence established unavailable TCP listeners while the Unix API remained alive. The experiment below then reproduced the kernel resource failure during direct uploads. Merely finding discarded server errors or unsupported RPC fragmentation would not have established that cause.

The existing write e2e tests mostly use the foreground `modalfs run`, one file, and Go writes. Add an experiment through the actual background daemon, with native copy processes, multiple files, incompressible multi-GiB data and the incident's 2 GiB shared cache. Monitor listing errors as well as latency, Unix API availability and browser TCP reachability. Check complete remote content through the control-plane/block API, independently of local caches. Run against the fake first for bounded network conditions, then real Modal using only a newly created scratch volume. The live path must not start Modal compute.

Investigate transport, local cache backpressure, write/commit interleaving and native-copy behavior separately. Record a failing baseline and an explanation of every wait/resource transition before changing production code. Passing tests constrain the tested conditions; they cannot prove arbitrary hardware, OS or remote-service behavior.

## Adjacent findings (not yet fixes)

- Daemon NFS and HTTP serve errors are discarded. Mount-table presence is treated as mounted even if the server is unavailable. These explain the misleading status but do not explain the sockets becoming CLOSED.
- The vendored NFS record reader rejects fragmented RPC records, and some connection error exits do not close the connection. There is no evidence yet that this incident involved fragmented records; it would also not by itself explain all listening sockets becoming CLOSED.
- One Linux CI run failed the unchanged `TestDownloadEndsByItsRecordWhenTheResultIsGone` with one completion event instead of two. A targeted 50-run check passed both on this branch and on the original `cc99faf` baseline. This remains an intermittent observation, not a diagnosed root cause, and no download code was changed.
- The 2-vCPU Linux VM's full fake-backed suite hit the eight-minute watchdog in `TestNoConflictWhileListing` and failed `TestStreamingReadThroughput`. The daemon dump shows directory lookup requests waiting behind a gRPC `List` stream through `cachedNames`; this is not evidence of an upload socket failure. The read-throughput limitation is already listed in `docs/known-issues.md`. Keep these results separate from the successful native-copy regression and the direct-Modal sustained-write run; do not describe the VM's entire suite as passing.

## Reproduction and resource evidence

`TestDaemonLargeNativeCopies` creates a fresh daemon and volume, then concurrently copies 3 GiB, 512 MiB and 64 MiB + 123 bytes from ordinary local files using `/bin/cp`. The test uses a 2 GiB cache and checks the Unix state API, browser TCP listener and native directory access. The sources use different ChaCha8 streams, so zero compression and repeated-block deduplication cannot disguise the transfer size. Remote verification streams every block into SHA-256, independently of the mount cache.

- Fake Modal at 20 MiB/s: all copies returned in 113.402 seconds. The first probe incorrectly applied the plain-directory 2-second threshold to native `ls`, which also stats changing files; it recorded 6.932 seconds. Corrected the probe to the existing file-stat threshold (45 seconds locally), retained error checks, and recorded this as an experiment correction, not a product fix.
- Direct real Modal, profile `topsoil-drakes`, scratch volume created at 03:33:51: the 3 GiB copy failed in 58.828 seconds with `fcopyfile failed: Operation timed out`, followed by chmod/xattr failures. The last committed prefix was 1,266,679,808 bytes. The browser TCP probe got ECONNREFUSED while Unix API latency remained below 62 ms. Test failed in 82.30 seconds and deleted its scratch volume. This reproduces the incident without using the user's volumes or starting compute.
- In that run, `kern.ipc.mbstat.m_forcedefunct` rose from 30 to 33; allocation failures rose from 3,048 to 37,584. The daemon's HTTP and NFS listening descriptors acquired state `0xa130` and error 9 (EBADF). `0x8000` is `SS_DEFUNCT`. An outbound connection sampled during the event held 3,707,116 unsent payload bytes and 7,557,120 bytes of kernel send-buffer memory; roughly 32 block-upload TCP connections were open.
- This host's TCP initial send buffer is 128 KiB, auto-growth ceiling 4 MiB, and maximum socket buffer 8 MiB. The upload transport never limits its send buffers. The adaptive upload controller measures bytes read from request bodies, before TCP has delivered them, and can permit 32 simultaneous uploads. Buffered bytes therefore look like upload progress and consume a large kernel allocation pool while the slow path drains them.
- Apple XNU's [`mbuf_watchdog_defunct`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/uipc_mbuf.c) selects the process holding the most socket memory and defuncts its sockets. [`sodefunct`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/uipc_socket.c) sets the exact state/error observed. No matching retained kernel log was available, so attribution uses the counter transition, descriptor states and isolated reproduction together.
- The fake already limits both accepted socket buffers to 256 KiB (`internal/modalfake/listener.go`, introduced in #16) specifically to avoid this watchdog. This protects the test server and applies receiver backpressure absent from real Modal. Existing live e2e also routes traffic through a local throttling proxy. Neither substitutes for a direct-WAN production-client test.

## Fix and rejected alternatives

Bound the production block transport's TCP send buffer before TLS starts, using the standard library's `TCPConn.SetWriteBuffer`, and fail the dial if that requirement cannot be applied. Use 256 KiB, the budget already used by the fake. At 32 connections this bounds configured send payload capacity to 8 MiB per client on macOS (kernel accounting includes overhead; Linux doubles the requested SO_SNDBUF value). This leaves transfer concurrency available for Modal's per-block latency and makes the application's writes experience backpressure earlier. This policy also applies before an HTTP proxy CONNECT request and to the optional HTTP/1 control-plane transport sharing this connection pool.

Do not merely raise NFS timeouts, enlarge the cache, restart a broken listener, or tune machine-wide sysctls: none removes the unbounded producer-side socket growth. Reducing upload concurrency alone sacrifices parallelism and still permits each remaining socket to grow with platform defaults. Changing the adaptive rate algorithm alone does not bound kernel allocation when the observed rate legitimately selects 32 uploads. A process-wide transfer scheduler would be larger and is unnecessary unless bounded sockets prove insufficient with multiple mounts.

Before the production edit, a local test drove the actual HTTP and TLS upload transport against a stalled receiver. Initially, the default loopback receive window did not trigger growth, so that passing experiment did not establish the invariant. Advertising a 4 MiB receive window before the handshake reproduced growth above the 512 KiB cross-platform budget in both protocols (663,084 and 548,396 bytes observed at failure). Both passed after the send-buffer limit. The test verifies a real kernel resource under traffic, not a mocked setter call.

## Verification scope and experimental corrections

The 3 GiB main file is a fast fault regression, not evidence that 20–100 GiB writes work. The final validation plan adds a 20 GiB native copy on macOS and a 100 GiB stream on Linux, each with a 2 GiB cache. The stream is produced by a separate process using a fresh ChaCha8 seed, with fsync before success. It retains only a 4 MiB write buffer and a SHA-256 state locally, so a 100 GiB source does not fill the VM's 100 GiB system disk. The native test retains multiple simultaneous copy processes and a partial final block in its smaller companion file.

The expensive sizes are opt-in through `just test-large-copy-live PROFILE 20` and `just test-large-stream-live PROFILE 100`; routine CI keeps the smaller real-mount fault regression. Total transfer/verification budgets scale with size, while individual API and native-directory latency bounds stay fixed. Failed service probes cancel the writer. Disk sampling checks the same cache allowance as the existing cache-pressure test: 2 GiB plus 64 MiB of concurrent in-flight writes. No machine-wide settings are changed.

The first fixed 3 GiB native copy completed in 67.504 seconds and committed its full 3,221,225,472 bytes, but the initial serial verifier hit its five-minute deadline. That run was not counted as a passing regression. The verifier now fetches URL batches and downloads four blocks concurrently, hashing in file order with at most 32 MiB of payload memory. For sustained tests it refreshes URLs every 2 GiB rather than depending on a long-lived URL list. These changes reduce verification overhead without sampling or omitting bytes. A subsequent complete direct-Modal run passed in 189.39 seconds: native copies took 56.893 seconds, all three SHA-256 hashes matched, maximum TCP probe latency was 1.596 ms, Unix API latency 5.042 ms, and native `ls` latency 9.516 seconds. The watchdog stayed at 33 and allocation failures at 37,584 through the fixed runs.

The native `ls` probe includes file stats, unlike `os.ReadDir`: macOS can flush pending writes before getting a changing file's attributes. Its bound is the existing `maxHeld` (45 seconds locally), while API probes retain `maxStall` (2 seconds locally). Fast errors fail too. The initial 2-second native-ls threshold was corrected explicitly rather than describing that result as a socket failure.

Linux validation uses the user's boxd VM (2 vCPU, 8 GiB RAM), through ego lite's web terminal. The supplied instabox SSH VM was suspended. No boxd/instabox CLI or library was installed. Go's normal toolchain selection obtained the repository's required version. TMPDIR points at the VM's disk because its default `/tmp` is a 3.9 GiB tmpfs. The boxd file uploader returned `machine not found`; the temporary live-test profile was instead written through a subprocess's stdin with terminal echo disabled, inside a 0700 directory with umask 077. Its contents were not printed or placed in shell commands/history.

The first 20 GiB run was cancelled by the native-directory probe at 50.002 seconds. It had uploaded about 5.5 GiB, its TCP/Unix probes were healthy, and its peak cache use was 2,056 MiB; there were no new socket reclamations or allocation failures. This is a failed test, but the copy was killed by the test rather than failing with an OS write error. A second run enabled the existing NFS trace without changing response bounds. A read-only `sample` of its blocked `ls` showed `fts_children → fts_build → advance_directory → getattrlistbulk`. Apple's [NFS getattr implementation](https://github.com/apple-oss-distributions/NFS/blob/main/kext/nfs_vnops.c) can invalidate/flush cached data when attributes change; identifying the user-space syscall alone does not prove which kernel branch ran. Preserve the latency observation rather than claiming the socket fix eliminates every delay during concurrent metadata reads.

That second 20 GiB run passed every hash and existing response bound in 1,171.92 seconds; native copies took 9m40.424s. The main file's SHA-256 was `d4d9d1e2be43f5d65f1572c756d614adcea7f58dc8bb476241c2087869cf881c`. Maximum Unix/TCP/native-directory probe times were 88.067 ms / 2.438 ms / 29.564 s, and cache peak 2,056 MiB. Kernel forced-defunct/allocation-failure counters remained 33 / 37,584. A separate normal-logging run is part of final acceptance so that trace instrumentation is not the only sustained native-copy evidence.

The first 100 GiB VM run was cancelled around 83 GiB by a successful Unix state response taking 2.282 seconds, above the developer-machine 2-second limit. It did not fail from an OS write error or an incorrect hash. Applying that timing profile to the 2-vCPU/8-GiB VM was a test-configuration mistake. Sustained VM acceptance uses the repository's existing `CI=1` constrained-runner budgets (15 seconds for general probes; 90 for native file-stat queries), with the same data, cache and full hash assertions. HTTP/TCP probe deadlines follow that budget instead of imposing an inconsistent shorter transport timeout. This cancellation is retained as evidence; it is not counted as a successful 100 GiB run.

## Decision checks

| Decision | Reason and tradeoff |
| --- | --- |
| Bound producer send buffers, keep upload parallelism | Remove the measured kernel-resource amplification while retaining concurrency that hides Modal's per-block latency. It may limit a single high-bandwidth/high-RTT flow; direct long-file tests measure the practical result. |
| Apply the transport policy on every supported OS | The resource problem is amplification in shared code; macOS has the particularly destructive watchdog response. Standard-library socket configuration avoids a platform-specific implementation or dependency. Linux's doubled accounting is explicit. |
| Fail a dial when buffer configuration fails | An unbounded silent fallback would restore the known failure path. Close that connection and propagate the error through existing transfer retry/reporting. |
| Keep journal, commit, conflict and mount identity code unchanged | Fix transport resource use without weakening write durability, crash recovery, conflict handling or account/volume pinning. Existing mounted e2e covers those invariants. |
| Use a real daemon and direct Modal block traffic | Match the app's ownership/lifecycle and expose the kernel buffering that the fake's bounded receiver and the usual live proxy can conceal. |
| Separate fault regression from sustained-size tests | 3 GiB reliably exposed this incident but cannot validate 20–100 GiB behavior. Keep routine CI affordable and provide explicit native-copy/stream recipes for the larger checks. |
| Fresh pseudorandom streams and complete remote hashes | Defeat compression and cross-run content deduplication; verify all bytes independently of both kernel and modalfs caches. |
| Stream the Linux source from a child process | Exercise 100 GiB on a 100 GiB VM disk without filling it with a source fixture or starting Modal compute. The tradeoff is that this case is a sequential writer, while macOS separately exercises native `cp`/`fcopyfile`. |
| Bounded parallel verification, expiring URL batches | Hide WAN round trips with four reads and 32 MiB of payload memory; renew URLs every 2 GiB. This changes neither expected content nor file-size checks. |
| Preserve unrelated failures and cancelled experiments | A green retry does not erase earlier evidence. Scope stays on large-write failures; separate read/listing and download-event observations remain visible for later work. |

All production clients still use the daemon's API; there is no new setting or UI behavior to localize. Tests use short, isolated homes with keychain access disabled and newly created scratch volumes. They only call Modal's control plane and signed block URLs. No real user mount was stopped or modified, and no release was deployed.

## Limits of the claim

The observed mechanism and its minimal resource fix have a failing direct-WAN baseline, a kernel-state/counter match and a passing exact-content regression. Finite tests cannot establish that arbitrary file sizes, link failures, unrelated programs exhausting the host's resources, or future kernel/Modal behavior are impossible. The chosen buffer budget is per connection/client, not a global daemon memory scheduler. For this failure mechanism, queued socket capacity is bounded by active connection count rather than cumulative file size; that is the reason the fix applies beyond the smallest reproduction, not a substitute for sustained-size validation.

The final acceptance record, including normal-logging 20 GiB and constrained-VM 100 GiB results, exact checks, residual observations and cleanup, is maintained in [PR #17](https://github.com/t41372/modalfs/pull/17). This document records the reasoning and failed experiments as well as the successful fault regression; the PR's acceptance table records the final measurements rather than duplicating a changing status here.
