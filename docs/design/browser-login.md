# Connecting an account in the browser

The primary connection action uses Modal's `TokenFlowCreate` and `TokenFlowWait`, as `modal token new` does. The daemon starts an anonymous client using the existing transport, gives the UI or CLI the returned URL and optional confirmation code, and waits for credentials. `AddAccount` validates and stores those credentials using the existing account store. No compute starts and no mount changes.

## Decisions and tradeoffs

- **Direct RPCs rather than running the Modal CLI.** The existing Go dependency supplies the messages and RPC methods. This adds no runtime dependency and never writes or activates a Modal CLI profile. These are internal upstream interfaces, so modalfs must follow changes to the official token flow.
- **Keep the existing paths.** CLI profile import remains available below browser login. Manual token entry stays as a subdued UI action, and `account add` keeps its scripting behavior. `account login` is the browser equivalent in the CLI; `--no-browser` prints the same link without opening it. Token replacement for an existing account is unchanged and outside this change.
- **A new login adds an account; it never replaces one.** Logging in again after a token was revoked adds a second account, usually with the same label, and the old account's mounts stay pinned to it. The user recovers by replacing the old token (Replace token, pasting a token from the same workspace) or by disconnecting the old account and adding its volumes again. This is acceptable only because a mount is cheap to set up again: it holds a handful of settings. Revisit this when an account or a mount starts holding anything costly to recreate (state or settings tied to its ID): then a login should be able to replace an existing account's token, or move its mounts to the new account, before that state ships.
- **Daemon ownership with independent attempts.** Each attempt has its own small state record, client and cancellation context, so a CLI and a window can connect independently. The wait secret and resulting token secret never go to UI clients. Accounts remain deduplicated by token ID, not workspace, so different users in the same workspace still work.
- **Ten-minute, memory-only attempts.** This is modalfs's deadline for waiting for approval, not a promise about how long Modal's link stays usable. Both clients show the deadline. Once Modal returns credentials, saving them has its own twenty-second validation limit and can finish after the waiting deadline. A daemon restart requires starting again; pending authentication is not journaled. Completed results remain available for at least ten minutes and are pruned when another attempt starts. This avoids a separate persistence format for temporary authentication state.
- **Explicit cancellation with an honest save outcome.** Closing the connection dialog or leaving its mounted view cancels that attempt; CLI Ctrl-C does the same once the attempt exists. Before that, Ctrl-C ends the CLI and disconnecting cancels creation of the login link. A per-attempt lock serializes cancellation with account saving. If saving has begun, cancellation can wait for validation/storage and returns the connected account when it succeeds or the save error when it fails. The CLI cancels only on request while it is still waiting; a completed result or failed status request needs no cleanup. A second Ctrl-C ends the CLI without waiting for the save's outcome. The global daemon lock never covers this work. Abruptly closing a browser window, killing its process or losing the client connection may prevent cleanup; the daemon's deadline still bounds waiting for approval. Cancellation stops local waiting, not an already issued token on Modal. During daemon shutdown, mounts are committed and unmounted before waiting for account saves to finish.
- **Simple polling and explicit recovery.** The UI asks the local daemon for status once a second while waiting. The daemon uses Modal's forty-second long poll and continues on its normal timeout response. A transport failure ends the attempt with an error and a new-login action, rather than retrying an operation whose result is uncertain. This avoids a new event transport or a hidden retry policy. A failed browser launch preserves the link; a failed clipboard write leaves a selectable URL and an actionable error.
- **The CLI's localhost validation endpoint.** A separate listener binds only to `127.0.0.1` and serves the public flow ID with the CORS header used by the official CLI. It never serves credentials or the wait secret. The daemon's authenticated API and its Host checks are unchanged. The listener and Modal connection close when the attempt finishes.
- **Open the browser on the daemon's machine.** This follows existing modalfs open actions: start the opener, report an error if it cannot start, and let it finish in the background. Some Linux openers stay running while the browser is open, so waiting for them would report a false failure. An opener that starts but then exits with an error cannot be detected, and whether the user actually sees a browser cannot be guaranteed. The printed/copied URL is available for manual opening, including from another computer. Modal may request the displayed confirmation code.
- **Use each surface's clipboard.** The app uses the already loaded Wails runtime's native clipboard; browser tabs use `navigator.clipboard`. A selectable URL remains available if copying fails. This avoids relying on browser clipboard permissions in the desktop WebView and adds no clipboard API to the daemon.

## Verification

The daemon tests use a real local gRPC server and an isolated credential store. They exercise anonymous start, the localhost flow-ID endpoint, long-poll timeout followed by approval, saving credentials without exposing either secret, network failure, cancellation before approval and cancellation during account saving, expiry of the wait, a save that finishes after the wait's deadline, an opener that stays in the foreground and a missing opener. The CLI tests run against a fake daemon socket and cover each final state, Ctrl-C while waiting (including a cancel that returns a save error) and Ctrl-C while the login is still being created. Existing profile import is also exercised through the mock UI.

UI QA covers light and dark themes, a 390-pixel viewport, copy and clipboard failure, cancellation, dialog closing, successful completion, failed login and retry, manual token access, and profile import. The real Modal API is checked only through creating an unauthenticated login link and cancelling it from an isolated daemon; no browser approval or credential creation is part of that check. Live browser approval and native WebView clipboard behavior remain manual verification items.
